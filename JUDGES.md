## The path

1. **The front page (30 s).** [porter-frontdesk.vercel.app](https://porter-frontdesk.vercel.app): the claim, "How it works" (hold, answer, approve) and "What runs where", one line per Otari feature with the identifiers behind it.
2. **A held injection (60 s).** On [/try](https://porter-frontdesk.vercel.app/try), pick **Hidden instruction**, then **File the issue**. The bug report carries an instruction in an HTML comment. The triage step ends with 403 `guardrail_violation`, no model is served (0 answer tokens), and the reply is Porter's fixed "passed it to a maintainer" text. **Open the full trace**: the triage step carries the guardrail result from Otari's 403 body (profile, score, porter-guard's explanation), and the guard service log lists each profile's verdict. *Verified: [run b3681e58](https://porter-frontdesk.vercel.app/console/runs/b3681e58-1db1-4077-a688-0055bd4ceb50).*
3. **A spam wave (45 s).** On /try, pick **Spam wave (12 issues)**, then **File 12 issues**. Twelve low-effort issues from your one visitor id run one after another against one allowance. As it drains, the triage step's model chip switches to DeepSeek V4 Flash (`deepseek-v4-flash-0731`) past 80 %; once it is spent, the remaining calls are refused at the gateway and the issue gets a fixed reply that names the reset time. Other authors' allowances do not move; the spend still counts against the desk workspace's daily ceiling. /try takes six filings an hour from each address. *The mechanism is verified on one visitor: [run 47a9bd89](https://porter-frontdesk.vercel.app/console/runs/47a9bd89-e206-4d35-aced-07a220bdf3cc) shows the tier-down model on triage and the budget refusal on repro.*
4. **The console (45 s).** [/console](https://porter-frontdesk.vercel.app/console): the queue with every run's outcome; **Authors**, whose meters are read from Otari's end users (Upgrade and Block call Otari's end-users API on the strangers key); **Waiting for approval**, where **Approve** runs the proposal through Otari's `/mcp/execute` on the maintainer key and the row turns executed. Proposals come from GitHub issues only (a /try issue gets a reply, never a label). *The first proposal, from porter-demo#11, is waiting; no approval has run live yet.*
5. **A run trace (60 s).** Open any run from the queue (`/console/runs/<id>`). Each step shows the routing policy Porter asked for, then the model and provider Otari served; a fallback badge with the attempt count when the first candidate failed; the cost; the Otari request id (copyable, it finds the same request in the Otari dashboard); guardrail results; the MCP and web fetch calls of the tool loop; on a repro step, a "ran in the sandbox · exit N" chip with the code and output Otari recorded; on the review step, the claims it struck for lack of evidence. *Good examples: [run d1c674d7](https://porter-frontdesk.vercel.app/console/runs/d1c674d7-895d-4cf8-a89d-88acf41050cc) (five MCP tools, sandbox, review), [run 7b2937f9](https://porter-frontdesk.vercel.app/console/runs/7b2937f9-f3b6-44ba-9f96-f16088c6403e) (a confirmed repro), [run 51cef7d6](https://porter-frontdesk.vercel.app/console/runs/51cef7d6-4e79-4de2-8554-22e92d721efb) (a web fetch and struck claims).*
6. **The eval (30 s).** [/eval](https://porter-frontdesk.vercel.app/eval): the same bot twice, Porter against prompt-only defences, on 25 attacks and 25 real Otari issues; where each attack stopped; the spam wave; the method, fixed in [eval/PREREGISTRATION.md](eval/PREREGISTRATION.md) before the first run. *Results pending.*
7. **The Otari report (30 s).** [/report/otari](https://porter-frontdesk.vercel.app/report/otari): Porter's read-only triage of a seeded sample of `mozilla-ai/otari`'s open issues, every claim marked with whether a person has checked it. Nothing is posted to that repository. *Results pending.*
8. **The code (the rest).** [README: How Otari is used](README.md#how-otari-is-used) names the file behind each Otari capability; [CHALLENGE_CHECKLIST.md](CHALLENGE_CHECKLIST.md) maps each requirement to evidence; [CLAIMS.md](CLAIMS.md) says how each public statement can be checked; [docs/architecture.md](docs/architecture.md) draws the trust boundaries.

## On GitHub

*Verified on [porter-demo#11](https://github.com/RaYYeR220/porter-demo/issues/11).* Open a test issue on the demo repository, [RaYYeR220/porter-demo](https://github.com/RaYYeR220/porter-demo) (the "Open a test issue" button on the front page goes there). Porter replies on the issue as `porter-front-desk[bot]` with a link to the run's trace; the run also appears in /console. Labels and a duplicate close show up as proposals. The repository's owner, members and collaborators can comment `/porter approve` (or `/porter reject`) on the issue instead of using the console; `/porter upgrade @user` moves an author to the larger allowance and `/porter block @user` stops automated answers to them. Issues from the owner get the same stranger treatment as anyone else's.
