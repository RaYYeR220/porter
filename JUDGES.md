## The path

1. **The front page (30 s).** [porter-frontdesk.vercel.app](https://porter-frontdesk.vercel.app): the claim, one measured result under it (labelled post-hoc), "How it works" (hold, answer, approve) and "What runs where", one line per Otari feature with the identifiers behind it.
2. **What was measured (60 s).** [/eval](https://porter-frontdesk.vercel.app/eval): the pre-registered tables first (where each attack stopped, in which arm, at what cost, and which real issues were held), then the post-hoc runs, each labelled as such. [README: What the results say](README.md#what-the-results-say) reads the same tables in words, the negative result first.
3. **One issue, end to end (45 s).** [porter-demo#11](https://github.com/RaYYeR220/porter-demo/issues/11): a stranger's bug report, Porter's reply as `porter-front-desk[bot]` with a link to its run, and the labels a maintainer approved.
4. **Its run page (60 s).** [run 994e344a](https://porter-frontdesk.vercel.app/console/runs/994e344a-8441-4249-8ed4-b83467d3c00b): each step shows the routing policy Porter asked for, then the model and provider Otari served, the cost and the Otari request id (it finds the same request in the Otari dashboard); the triage step lists the MCP calls of the tool loop, the repro step has a "ran in the sandbox · exit N" chip with the code and output Otari recorded, the review step lists the claims it struck, and the proposal shows executed through `/mcp/execute` on the maintainer key.
5. **A held injection (45 s).** [run b3681e58](https://porter-frontdesk.vercel.app/console/runs/b3681e58-1db1-4077-a688-0055bd4ceb50): the /try **Hidden instruction** preset, refused by Otari at triage with 403 `guardrail_violation` before any model ran, and Porter's fixed "passed it to a maintainer" reply. The triage step carries the guardrail result from Otari's 403 body; the guard service log lists each profile's verdict. To see it yourself: on [/try](https://porter-frontdesk.vercel.app/try), pick **Hidden instruction**, then **File the issue**.
6. **One author's budget (30 s).** [run 47a9bd89](https://porter-frontdesk.vercel.app/console/runs/47a9bd89-e206-4d35-aced-07a220bdf3cc): a visitor past 80 % of their allowance got triage from DeepSeek V4 Flash (`deepseek-v4-flash-0731`), the tier-down model, then a 403 `budget_exceeded` on repro and a reply naming the reset time. Other authors' allowances do not move. On /try, **Spam wave (12 issues)** drains one allowance the same way; /try takes six filings an hour from each address.
7. **The console (30 s).** [/console](https://porter-frontdesk.vercel.app/console): the queue with every run's outcome; **Authors**, whose meters are read from Otari's end users (Upgrade and Block call Otari's end-users API on the strangers key); **Waiting for approval**, where **Approve** runs a proposal through Otari's `/mcp/execute` on the maintainer key. Proposals come from GitHub issues only (a /try issue gets a reply, never a label). More run pages: [run d1c674d7](https://porter-frontdesk.vercel.app/console/runs/d1c674d7-895d-4cf8-a89d-88acf41050cc) (five MCP tools, sandbox, review), [run 7b2937f9](https://porter-frontdesk.vercel.app/console/runs/7b2937f9-f3b6-44ba-9f96-f16088c6403e) (a confirmed repro), [run 51cef7d6](https://porter-frontdesk.vercel.app/console/runs/51cef7d6-4e79-4de2-8554-22e92d721efb) (a web fetch and struck claims).
8. **The Otari report (30 s, optional).** [/report/otari](https://porter-frontdesk.vercel.app/report/otari): Porter's read-only triage of a seeded sample of `mozilla-ai/otari`'s open issues, each with its run trace and cost, every claim marked with whether a person has checked it. Nothing was posted to that repository, and the share of correct claims stays empty until someone checks them. [README: What the results say](README.md#what-the-results-say) tells what the two unpublished runs before it found, and the commits that fixed it.
9. **The code (the rest).** [README: How Otari is used](README.md#how-otari-is-used) names the file behind each Otari capability; [CHALLENGE_CHECKLIST.md](CHALLENGE_CHECKLIST.md) maps each requirement to evidence; [CLAIMS.md](CLAIMS.md) says how each public statement can be checked; [docs/architecture.md](docs/architecture.md) draws the trust boundaries.

## On GitHub

*Verified on [porter-demo#11](https://github.com/RaYYeR220/porter-demo/issues/11), including an approved proposal.* Open a test issue on the demo repository, [RaYYeR220/porter-demo](https://github.com/RaYYeR220/porter-demo) (the "Open a test issue" button on the front page goes there). Porter replies on the issue as `porter-front-desk[bot]` with a link to the run's trace; the run also appears in /console. Labels and a duplicate close show up as proposals. The repository's owner, members and collaborators can comment `/porter approve` (or `/porter reject`) on the issue instead of using the console; `/porter upgrade @user` moves an author to the larger allowance and `/porter block @user` stops automated answers to them. Issues from the owner get the same stranger treatment as anyone else's.
