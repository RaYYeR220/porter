# Feedback on Otari

Written answers to the three feedback questions, from building Porter on hosted Otari. The feedback video (3:34) is at https://youtu.be/2TkA2zo2TNo.

## When were you most tempted to skip Otari and call the provider directly? What happened?

When I got to guardrails. On otari.ai the built-in `prompt-injection` profile has no service behind it, and every catalog guardrail needs a vendor key (#2722, #2937). Calling Llama Guard from my own code would have been the quick way out. Instead I wrote porter-guard, a small `/validate` service whose classifiers (Qwen3Guard, gpt-oss-safeguard, Llama Guard 4) also run through Otari, and mandated it on the bot's workspace. The edges took a while: `valid: null` passes in block mode (#2788), a request-level credential is dropped (#2955), the mandate's Endpoint wants the base URL because Otari appends `/validate`, and the guard sees only the user message, not the system prompt. The second temptation was models: on my full triage request (strict JSON, a stored MCP server and web fetch together) gpt-oss-120b often ended with empty content and its tool arguments in `reasoning`, while a one-line MCP request worked, so I suspect my prompt shape rather than the gateway. Instead of leaving the gateway I changed one routing policy: triage moved to DeepSeek V4.1 Flash, with gpt-oss-120b kept as the last fallback. I'm glad I stayed: the guard now screens every call made with that key, including paths I forget about, and on a smaller model it let 0 of 25 attacks through where the prompt-only version leaked 2.

## What did you end up building yourself that Otari should've done for you?

Three things. First, the guard service above. Second, an output check: gateway guardrails are input-only (`output` is accepted but not enforced), and for a bot that posts replies to strangers the reply is where a hijack shows, so Porter checks every reply for off-allowlist links, a per-run canary, raw HTML and invisible characters. Third, the setup: budgets, ceilings, service keys, routing policies, the MCP server and the mandate are dashboard-only on hosted, so the README has eight manual steps, budget ids have to be copied out of the key dialog, and I regenerated five keys by hand when I lost them. Smaller things I hit on live traffic: hosted web fetch rejects `max_uses` and `allowed_domains` on the request, so the allowlist lives in the workspace; the EU org gets a 421 on the default US host; and on a fresh account the "Personalize Otari" survey sits over every dashboard route until it is answered or skipped.

## If the rules hadn't required Otari, would you have continued using Otari? Why or why not?

Yes, for this app. A service key with end users gives every issue author their own daily budget without me keeping a ledger. The best lesson came from measuring it: at open-weight prices a spam "+1" costs about $0.0008, so a $0.05 daily cap let a spammer get 20 answers. Adding a request limit to the same end-user budget cut that to 6 answers and $0.0036, with no code change. One tier-down policy moves a noisy author to a cheaper model at 80 %, and the 403 with Retry-After at the cap becomes a polite reply with the reset time. `otari_tool_calls` proves a snippet really ran in the sandbox, with its exit code, so I never take the model's word for it. A stored MCP server with an `@read` grant keeps strangers away from write tools, and `/mcp/execute` gave me a maintainer approval step without a second tool runtime. Output guardrails and an admin key for setup-as-code would make it an easy yes without the rule.
